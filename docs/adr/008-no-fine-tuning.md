# ADR-008: No fine-tuning — prompt + routing is the contract

**Status**: accepted
**Date**: 2026-05-26
**Deciders**: Álvaro

## Context

The first instinct on hearing "build a coding agent" is to fine-tune a model on tool-use
trajectories. SWE-agent and similar projects do this. Should we?

Constraints:
- Solo project, no GPU budget.
- Groq Cloud (ADR-009) does not host custom fine-tunes — it serves a fixed set of
  open-source models. Fine-tuning means hosting elsewhere (Together, Anyscale, vLLM
  self-hosted) and giving up Groq's throughput.
- The portfolio signal we want is "I can engineer agents", not "I can train models". Those
  are different jobs in the market.

## Alternatives considered

1. **SFT (supervised fine-tuning)** on synthetic tool-call trajectories generated by the
   agent itself, then training a smaller model to imitate the larger one. Pros: cheaper
   inference; possibly better tool format adherence. Cons: needs GPU compute, evaluation
   infrastructure, ablation discipline; the result is hard to defend in interview without
   "show me the loss curves and the held-out eval".
2. **DPO / RLHF** on success/failure pairs from `evals/runner.py`. Same cons, plus a much
   larger eval dataset is required to avoid overfitting to 10 trivial issues.
3. **Prompt + routing only** — invest the budget in better prompts (system / planner /
   verifier), better tool schemas, and the multi-model routing in [ADR-004](004-multi-model-routing.md).
   Each change is measurable on the eval set in minutes, not hours.

## Decision

No fine-tuning in this project. The contract is **prompt + routing**. Improvements to
resolved@1 come from:
- Better system prompt and per-role prompts (planner, executor, verifier).
- Better tool descriptions (the model uses the schema's `description` field to choose tools).
- Better routing (ADR-004), including A/B testing models for each role.
- Better self-correction loop (ADR-002, Semana 2) — Reflexion-style retry on verifier rejection.

## Consequences

**Easier**:
- Iteration speed: a prompt change is one file + one `python -m evals.runner` away from a
  measured delta. A fine-tune is hours to days.
- The codebase stays defendible: every behavioural change is a diff in a `.py` file, not
  a "we trained a model and now it's better, trust us".
- Cost stays $0 on Groq free tier. A fine-tune-host-serve loop costs.

**Harder**:
- There is a ceiling on resolved@1 we cannot cross by prompt alone. When we hit it, the
  honest move is to document the ceiling and stop, not to silently start fine-tuning.

**Accepted**:
- Lower theoretical maximum resolved@1 than a well-tuned model. The portfolio narrative
  ("I built a hand-rolled agent that hits X% on SWE-bench Lite with open-source models") is
  stronger than the alternative ("I fine-tuned a model to hit X%") in the AI Engineer hiring
  funnel: the second one invites the interview question "what was your hyperparameter sweep?"
  which we cannot honestly answer without the GPU budget we don't have.

## Verification

This ADR is verified by what we **don't** see in the repo: no `training/`, no `data/`, no
`finetune.py`, no model artifacts in releases. If any of those appear, the ADR has been
violated and needs an updated decision record.

When the prompt-only ceiling is hit (resolved@1 plateau on SWE-bench Lite across three
consecutive prompt iterations), we revisit this ADR rather than silently change the contract.
